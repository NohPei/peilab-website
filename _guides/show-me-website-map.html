What makes this modular?

  1. Content is independent

    Each member can add a file without editing another person's work or a long shared page.

  2. Lists build themselves

    Listing pages read the collections. A new project appears on the projects page automatically.

  3. Design has one home

    Cards, navigation and profile photos live in reusable templates. A design fix updates all matching pages.

  4. Assets have clear owners

    Keep figures under the project or post name. Use descriptive lowercase filenames, without spaces.

A repeatable update workflow

Recommended team workflow
1. Edit locally

Update source files and assets on your computer. Preview and run the checks.

→
2. Push to GitHub

Commit and push the source for shared history, review and merge. GitHub does not deploy this site.

→
3. Copy the build to vhosts

Build the saved version locally, then upload _site/ to /w/peilab/. Verify the public pages.

Make website edits locally. GitHub stores the source and history; the U-M vhost serves the generated files. Do not edit website files directly on the remote vhost. GitHub access and server-folder write access are separate permissions.

Team review: use the pull request steps below. An authorized maintainer publishing an approved update may instead push reviewed commits directly to main when repository rules permit. Both paths end with the same sequence: save the source on GitHub main, build that commit locally, then copy the generated files to vhosts. The upload changes the public site; the GitHub step preserves the source and its history.

Start from main. The earlier website-maintenance branch is already incorporated into main. It is not a second website or a publishing branch. Create new contribution branches from up-to-date main.

The header between --- lines is called front matter: it supplies the title and other page metadata. The default post template is configured centrally. The text in ![…] describes the image for accessibility.

Post filenames follow YYYY-MM-DD-title.md. For the first post, set published: true in news.md and add a /news/ link in _data/navigation.yml.

From edit to published page

  1. Copy a content template locally

    Choose a person, project, paper or post template. Fill in its required fields in your local repository.

  2. Add text and assets

    Put figures in the matching image folder. Check the filename and letter case in each reference.

  3. Preview locally

    Start Docker Desktop, then run:

    docker compose up

    Open localhost:4000. Check the page, images, links and mobile layout. Restart the preview after configuration changes.

  4. Commit, push and open a pull request

    Save source content, assets and relevant documentation together. Push your branch to GitHub and describe the update for review. Keep generated _site/ files out of Git.

  5. A maintainer publishes the saved version

    After review and merge, update local main, confirm a clean working tree and record the commit. Back up the live site and generate a production build locally. Upload with rsync -rlcP as described in README.md; compare remote contents and verify public pages. Review removed pages separately. If a server folder blocks writes, its owner or an administrator must restore peigroup access before deployment is complete.

What “copy to vhosts” means

Source on GitHub main

Markdown, templates and assets, with a shared change history.

→
Build locally

Stop the preview. Jekyll generates production files in _site/.

→
Upload the contents

rsync copies the generated files into /w/peilab/ on the U-M server.

Local: _site/publication/index.html
Server: /w/peilab/publication/index.html
Public: https://peilab.eecs.umich.edu/publication/
  1. PowerShell: save, check and build

    Push the approved source to main, confirm local and GitHub commits match, stop the preview and make the production build.

  2. Local WSL/Bash: sign in and back up

    Open Ubuntu on your computer, enter the repository folder, authenticate to vhosts with your U-M account and back up the current server files.

  3. Local WSL/Bash: preview, upload and compare

    A dry run with rsync -rlcni lists differences. After review, rsync -rlcP uploads them; repeat the dry run to confirm they match. Keep the trailing slash on _site/ to copy its contents into the web root.

  4. Browser: verify the public page

    Check the page, links and images. Record the source commit, uploaded paths and backup. Close the temporary SSH connection when finished.

Use the commented commands in README.md for the complete login, backup, upload and verification steps. Commands run on your computer; do not edit website files on the remote server.

Permissions are specific to a path. The People listing (people/index.html) and an individual profile (people/ellina_ho/index.html) are separate files. A targeted upload can succeed while another folder remains blocked; verify and report its exact scope. Include all affected pages and assets, and review obsolete remote files separately.

Documentation and this guide stay on GitHub and are excluded from the public build. Documentation-only updates need no vhost upload.

Keep updates easy to review

  1. Use one file per content item and keep existing filenames stable to preserve URLs.
  2. Commit each content file and its images together.
  3. When the project structure or contribution workflow changes substantially, update this visual guide in the same change. Explain what contributors need to know; routine content edits do not need a guide update.
  4. Run the content check: docker compose run --rm --entrypoint ruby jekyll scripts/validate.rb.
  5. Run the template/build check: docker compose run --rm -e JEKYLL_ENV=production --entrypoint ruby jekyll scripts/check-build.rb.
  6. Open a focused pull request. Automated checks validate content, images and generated pages.
